# アプリ起動・終了とCDTimerの常駐

PW-H1のROMダンプにある `DicMain.bin`、`SHARP/SharpLib/SharpLib.bin`、
`ToolsApp/CDTimer/AppMain.bin` と、V690_H1から抽出した `system.bin` の静的解析。
以下のオフセットは各ファイル先頭基準。実機での常駐成功は未確認。

## 起動スロット

SharpLib API `0x84010138` → `0xe69f4` は、r0にPresentation、r1に実行パス、
r2に追加文字列、r3にスロット番号を受け取る。スロットごとに64バイトの管理領域を使用し、
`0x8604301c + slot * 64 + 4` が非ゼロなら新規ロードしない。

`0xe6a38..0xe6a50` でシステム制御 `0x10020` にスロット番号を渡し、
8バイトのアドレス対を取得する。ファイルを第2アドレスへ読み込み、キャッシュ関連の
処理を経て第1アドレスへ `BLX` する（`0xe6af0..0xe6b6c`）。
アプリへ渡すr0はそのスロットの管理領域。

| スロット | 用途 | 実行アドレス | ファイル読込アドレス |
| --- | --- | --- | --- |
| 1 | Calcなど | `0x83000000` | `0x66a00000` |
| 3 | CDTimer | `0x83400000` | `0x66e00000` |
| 5 | eNote | `0x83800000` | `0x66f00000` |
| 7 | WritingBoard | `0x83c00000` | `0x67000000` |
| 10 | 追加アプリ | `0x90000000` | `0x67100000` |

アドレス対はsystemの `0x8fe94..0x8ffc8` の分岐表。
第2アドレスを各アプリの `.data` 配置アドレスと混同しない。

DicMainの `0x32c918` はツール番号をスロット番号へ変換する。
表はファイル `0x850a1c` の13個のu32で、
`[1,3,0,6,5,4,2,0,7,9,8,0,11]`。
パスの表は初期化後RAM `0x850021c8` にあり、先頭3件は
`ToolsApp\Calc`、`ToolsApp\CDTimer`、`ToolsApp\eMemo`。
従ってツール番号1のCDTimerはスロット3となる。
追加アプリの起動経路は `0x3d5bec/0x3d5bfc` でr3=10を設定し、
`0x3d5c0c` → SharpLib APIへ渡す。

CDTimerのコードと初期化データは `0x83400000` / `0x86c00000` 向け。
Reflexは `0x90000000` / `0x90500000` 向けにリンクするため、
現状のAppMain.binをそのままスロット3へ渡すことはできない。

## 終了通知とホストの復帰

SharpLibは起動後にメッセージ `kind=0x10e, param=1, data[0]=slot` を送り、
終了API `0x8401013c` → `0xe6bdc` は実行パスからスロットを探し、
パスなどの管理メモリを解放して `kind=0x10e, param=2, data[0]=slot` を送る。
アプリのウィンドウやタイマーまでこのAPIが片付けるわけではない。

DicMainの `0x549700` は終了通知を処理する。
`0x549718..0x549734` でスロット0/10/11を通常アプリの復帰経路へ分岐し、
1〜9は `0x549980..0x5499c0` へ進む。画面・フォーカス・遷移状態の扱いが異なる。
ウィンドウを隠すだけでは、この終了・復帰処理は実行されない。

## フォーカスと `Presentation + 0x18c` の区別

以前のReflexの `set_current` は `Presentation + 0x18c` にウィンドウポインターを
書いていたが、これは誤り。DicMainは `0x549734..0x549740` でこの値を読み、
`0x54984c` 以降で上位16ビットの `0x10000/0x20000/0x30000` や
下位16ビットの `0x401d` を使って復帰先を分岐する。
CDTimerの終了処理 `0xa63b0..0xa63c0` はこの欄へ0を書いて終了通知を呼ぶ。
少なくとも通常のフォーカス先ポインターとしては扱えない。

実際のフォーカス移動はDicMain `0x549798..0x5497a0` → thunk `0x250dac`
→ API `0x60005330` → system `0x31a4c`。
対象の状態ビット `0x01` と `0x40` を検査し、フォーカス通知や親子関係を処理する。
ReflexはこのAPIを `move_focus` として使用し、`+0x18c` の保存・上書き・復元を廃止した。
これはソフトロックの原因候補となる実装ミスだが、修正による復旧は実機未確認。

## Inspectorの小窓テスト

CDTimerはコンストラクターに `0x08000001` を渡し、状態 `0x4010` を追加、
`0x08` と `0x40` を解除する。純正の状態のままでは、小窓へキーボードフォーカスを
移すAPIが対象を拒否する。本体を隠してHキーで戻す実験には、そのまま流用できない。

Inspectorでは本体非表示中だけ小窓に `0x40` を追加し、`move_focus` を呼ぶ。
本体表示時には本体へフォーカスを戻して小窓の `0x40` を解除する。
上段6キーはInspectorのモード切り替えとして扱い、小窓から純正ハンドラー経由で
別アプリを起動する試験経路は外した。

本当の常駐には、専用領域向けのリンク、スロットの使用状況、起動側の登録と通知、
辞書切り替え時のコード・データ・コールバックの寿命を合わせて調べる必要がある。
別スロット起動の実験は [brain-resident](../crates/brain-resident/README.md) に追加した。
Inspectorが空きスロット3へ同梱のResident.binを起動し、常駐側が独立して終了通知を送る。
ネイティブローダーの失敗経路では管理領域のパス欄が残る可能性があるため、
Inspectorはロード前にファイルの存在とサイズも確認する。失敗後の管理領域を直接書き換えて再利用はしない。
