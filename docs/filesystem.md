# V690_H1 ファイル操作 API

`SH_DIC_UPDATE_V690_H1.SDU` の `system.bin` を静的解析した記録。
名称は以下の実装から付けた仮称。公開入口は実行時アドレス、実装欄はファイルオフセット。
`system.bin` のロード先は `0x60002400`。
実機での列挙・読み取り・書き込み・エラー時の挙動は未確認。

## 読み取り用の公開入口

| 公開入口     | 実装                  | C ABI と結果                                                         |
| ------------ | --------------------- | -------------------------------------------------------------------- |
| `0x60006400` | `0xa067c` → `0x1d398` | `fopen(const char *path, const char *mode)` → pointer、失敗は null   |
| `0x60006404` | `0xa06fc` → `0x1d008` | `fclose(pointer)` → 0、失敗は -1                                     |
| `0x6000640c` | `0xa0724` → `0x1d4c8` | `fread(void *out, i32 size, i32 count, pointer)` → 要素数、失敗は -1 |
| `0x60006414` | `0xa07ac` → `0x1d5ec` | `fseek(pointer, i32 offset, i32 origin)` → 0、失敗は -1              |
| `0x60006454` | `0xa0cb0` → `0x1cea8` | `opendir(const char *path)` → pointer、失敗は null                   |
| `0x60006450` | `0xa0df0` → `0x1cf54` | `readdir(pointer)` → 下記エントリー、終了またはエラーは null         |
| `0x6000644c` | `0xa0d88` → `0x1cf30` | `closedir(pointer)` → 0、有効なハンドルは解放される                  |

`0x4000` などのエクスポートテーブルから上記実装への ARM B 命令を照合した。
Reflex の `fs` は `experimental-runtime` と ARM / `target_os = "none"` の組み合わせで公開する。
`open` はファームウェアと PEG スレッド上での直列呼び出しを前提とする unsafe API。
生成したハンドルは Rust の Drop で閉じる。File は明示的な `close` でエラーも取得できる。

## ファイルの読み取り

`0x1d398` は mode の先頭 `r` を `0x1d3c4` で受け付け、
`+` のない場合は下位 open に flags=0 を渡す。閲覧・コピー元の読み取りはこのモードを使用する。

`0x1d4c8` は size×count バイトを読み、読み込んだバイト数÷size を返す。
Reflex は size=1 で呼び、戻り値をバイト数として扱う。
短い読み取りは EOF、負値はエラーとして区別する。
`fseek` の origin=0 を使って先頭基準で移動する。offset は符号付き32ビット。

## ファイルの書き込み

以下は静的解析結果。Reflexの `File::create`（w）、`File::update`（r+）、`write`、`flush` に対応する。
`create` は切り詰めを伴うため、Explorerでは新規作成した専用の一時フォルダー内だけに使用する。実機での書き込みは未検証。

| 公開入口 | 実装 | C ABI と結果 |
| -------- | ---- | ------------ |
| `0x60006410` | `0xa0768` → `0x1d6cc` | `fwrite(const void *data, i32 size, i32 count, pointer)` → 要素数、失敗は -1 |
| `0x6000641c` | `0xa080c` → `0x1d058` | `fflush(pointer)` → 0、失敗は -1 |
| `0x60006430` | `0xa0978` | `ferror(pointer)` → ハンドルに保存されたエラー値 |

`fopen` は `r` に加えて `w` / `a` と、2文字目の `+` を認識する。
`w` は作成・切り詰め用の下位 flags=`0x601`、`a` は作成・追記用の `0x209`、
`r+` は更新用の `2` を渡す。再開書き込みは `r+` で開いて `fseek` する形が候補。
`w` を再開に使うと既存内容を失う。`a` は末尾への追記用。
モード判定は先頭2文字だけなので、`rb+` の `+` は認識されない。更新には `r+` を使う。

呼び出し順序は、`fopen(path, "w")` → `fwrite(data, 1, length, file)` →
`fflush(file)` → `fclose(file)`。open の null、write の要求バイト数との一致、
flush / close の戻り値をそれぞれ確認する。途中で失敗しても有効なハンドルは閉じる。
size=1、count は正の i32 の範囲に分割し、空データでは write を呼ばない。

実装上の注意点:

- `fwrite` は1024バイトの内部バッファを使う。成功しても下位書き込みがまだ行われていない場合がある。
- `fflush` はバッファを下位 write (`0x106b8`) に渡す。短い書き込みでは未書き込み分を残して -1 を返す。
- `fwrite` の途中の flush が失敗すると、一部を処理済みでも -1 を返し得る。全体をそのまま再送すると重複するおそれがある。
- `fclose` は flush と下位 close を実行し、どちらかが失敗すると -1 を返す。失敗時もハンドルを解放するため、同じハンドルを再利用しない。
- `fflush` の存在だけでは、SDカードへの永続化を保証する `fsync` 相当の処理まで確認できたことにはならない。

実機検証は SD0 の検証専用ファイルで行い、書き込み後の再オープン・読み戻しで内容を照合する。
ROM への書き込み可否は未調査。USB転送中の電源遷移抑止については [power.md](power.md) を参照。

## ディレクトリーエントリー

`0xa0cb0` は280バイトを確保し、先頭8バイトを管理用に使用する。
`0xa0df0` はエントリーを更新し、ハンドル+8を返す。
返却ポインタからの配置は以下。次の read / close より前に必要なデータをコピーする。

| 相対位置 | 型        | 内容                    |
| -------- | --------- | ----------------------- |
| `0x00`   | u32       | 種別。2がディレクトリー |
| `0x04`   | u32       | サイズ                  |
| `0x08`   | u32       | 名前の長さ              |
| `0x0c`   | char[260] | NUL終端のファイル名     |

`0x1cf54` は下位列挙APIのメタデータからサイズ・長さ・種別を取り出す。
`0xa0e44`〜`0xa0e4c` が名前をコピーし、`0xa0e8c`〜`0xa0e9c` が種別とサイズを設定する。
種別3を先に取得した場合は名前を保持しながら後続レコードを読み進める分岐もある。
名前は表示用の文字列へ変換せずバイト列として保持する。

列挙APIは EOF と読み取りエラーをともに null で返すため、列挙途中の障害と正常終了を区別できない。
SDカードの取り外しなどで一覧が途中までになる可能性が残る。
下位APIによるエラー判定は今回のラッパーには含めない。

## パスと検証

`system.bin:0x10e8e8` に `SD0:\APP\_debug\appmain.bin`、
`0x10e904` に `ROM:\version_.txt` がある。Explorer は `SD0:\` / `ROM:\` を入口にする。
パスは最大259バイト＋NUL。ディレクトリー名は階層ごとに保持し、親へ戻るときに
文字コード内の `0x5c` をパス区切りと誤認して分割しない。

ホストで確認できるのは画面・ナビゲーション・ページ境界と公開入口の分岐先まで。
実機では SD0 / ROM の一覧、長い名前、空ファイル、複数ページの読み取り、
終了後の画面復旧、カード未挿入時の挙動を確認する必要がある。
EOF / エラーの区別、文字コード、フォルダー種別・サイズは実機でも照合する。

## 作成・移動・削除・メタデータ

| 公開入口 | 実装 | C ABIと結果 |
| --- | --- | --- |
| `0x60006434` | `0xa0b84` → `0x11c64` | `remove(const char *path)` → 0、失敗は負値 |
| `0x60006438` | `0xa0b04` → `0x11ddc` | `rename(const char *source, const char *destination)` → 0、失敗は負値 |
| `0x6000643c` | `0xa0be4` → `0x11ba0` | `mkdir(const char *path)` → 0、失敗は負値 |
| `0x60006440` | `0xa0c50` → `0x11c64` | rmdir相当。removeと同じ下位入口 |
| `0x60006444` | `0xa09f0` → `0x12008` | `stat(const char *path, Metadata *out)` → 0、失敗は負値 |

`0xa0c00`〜`0xa0c14` は下位作成関数へ種別2・権限0777・追加引数0を渡す。
`0x95b78`〜`0x95b90` でもstatの失敗後にこのmkdir入口を呼ぶ。
renameは2つのパスを解決し、`0x11f3c`〜`0x11f50` で異なるファイルシステム間の移動を拒否する。

Metadataは20バイトで、modeが+0、時刻相当の3ワードが+4〜+12、**ファイルサイズは+16**。
`0xa0a98`〜`0xa0ab4` の5ワード書き込みと、`0x10e31c`〜`0x10e360` が
stat出力の+16をファイルサイズとして比較・freadへ渡すことを照合した。
modeの `0xf000` 部分が `0x4000` ならディレクトリー。
FAT の名前検索は `0x183ec` でエントリーを列挙し、名前が一致するまで検索する。
列挙が正常終了（0）しても一致しなかった場合、`0x184b4`〜`0x184b8` で `-0x460d` を返す。
この値は `0x11538` → `0x10b54` → `0x120b0` → `0xa0ab8` を経由して公開statにも返る。
Explorerは `-0x460d` だけを「保存先なし」とし、他のstat失敗では変更を止める。
従来の `-0x4603` 判定は誤り。`0x10b68` は探索対象のファイルシステムがなくなった経路で、
FAT の `0x17e44`〜`0x17e48` でも短いエントリー読み取りに `-0x4603` を返すため、未存在として扱わない。

Explorerは変更前にSD0配下かを確認し、保存先が存在すれば拒否する。空フォルダー削除も列挙で確認し、再帰削除は行わない。
存在確認からrenameまでを一体化した排他的操作ではないため、処理中に他のアプリ・PCから変更しない。
列挙APIのEOF／エラーの曖昧さは残る。実機での非空フォルダー拒否・カード障害時の戻り値は別途検証が必要。

## 純正アプリのデータ保存パス

V690_H1 の展開済み `packages/001/ROM` にある純正アプリ14個、
その展開済みRAM初期値、`DicMain.bin`、`SharpLib.bin`、`system.bin` を調査した。
下記のオフセットは、特記しない限り各アプリの `AppMain.bin` 内のファイル位置。
保存済みの実機ファイルを取得した結果ではない。

### 保存先の分かれ方

- `USR:`：カレンダー、ローマ字練習、ノートなどのユーザーデータで使われる。
- `SYS:`：電卓・時間割・タイマー・録音の設定などで使われる。
- `SD0:`：SDカード。ノート・録音には `USR:` と `SD0:` の両方のパスがある。
- `AKM:`：`DicMain.bin` と SetMenu に `AKM:\TMEMO` がある。データ内容は未確定。
- `ROM:`：アプリ本体と同梱リソース。アプリの配置場所がそのまま保存先になるわけではない。

これは使用例による分類であり、ドライブごとの用途を網羅した定義ではない。
`system.bin:0xcdf5c`～`0xcdf7c` に `ROM:` / `SYS:` / `LOG:` / `AKM:` / `USR:`、
直後に `file_system_init()` と `emmc0*` の文字列がある。
USB側にも各ドライブの別モードが存在する（[USB解析](usb.md#pc側はusb-mass-storage)）。
物理パーティションとの対応や容量、アクセス権は今回確定していない。

### 読み書きまで確認した経路

Calendarの `0x89384` は `calendar.bin` をstat後に `r+b` で開き、
`fread(buffer, 16, count, file)` で読み込む。
`0x893e0` は同じパスを `w+b` で開き、`0x89408` で
`fwrite(buffer, 16, count, file)`、`0x89410` でcloseする。
`0x87d5c` / `0x87d64` / `0x87d84` / `0x87d6c` のジャンプ先はそれぞれ
公開入口 `0x60006400` / `0x6000640c` / `0x60006410` / `0x60006404`。
少なくともこのファイルは16バイト単位のレコード列として扱われる。フィールドの意味は未解析。

Calcの `0x155678` は固定パス `SYS:\ToolsApp\calc.ini` を返す。
読み込み側は `0x152f20` → `0x15362c` で `rb`、
書き込み側は `0x152f40` → `0x1536fc` で `wb` を使う。
書き込み前に `0x153744`～`0x153748` で `SYS:\ToolsApp` のmkdirを呼ぶ。
`0x15379c` と `0x1537b4` はデータ本体と追加2バイトをfwriteへ渡す。
拡張子は `.ini` だが、一般的なテキストINIとして編集できるとは限らない。

### Explorerとの関係と未確認事項

Explorerのルートに `SD0:` / `ROM:` に加えて `USR:` / `SYS:` / `AKM:` を追加した。
本体側の保存先も既存の列挙・閲覧・USB送信を利用できる。書き込み先は従来どおり `SD0:` に限定する。
本体側ドライブの実機での列挙と実ファイルの取得は未確認。
設定ファイルの直接編集や削除は、形式と復旧方法を確認してから行う。

実機でのファイルの存在、保存タイミング、SD未挿入時の挙動、ドライブ間の切り替え条件、
設定・履歴の完全なバックアップ手順は未確認。
