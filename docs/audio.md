# V690_H1 音声 API の解析

SDU の `packages/002/ROM/SHARP/SharpLib/SharpLib.bin`、`system.bin`、
`packages/001/ROM/App/pvss/AppMain.bin` を静的解析した結果。
以下の関数名は解析用の仮称であり、実機での再生・録音は未確認。
再生に必要な入口を Reflex の実験的な `audio` モジュールに追加し、Doom の効果音出力に使用する。
録音・シークはまだラップしていない。

## 呼び出し先

SharpLib の公開入口は実行時アドレス。実装位置と kernel の位置はファイルオフセット。
SharpLib のロード先は `0x84000000`、system はファイル位置に `0x60002400` を加える。

| 公開入口     | SharpLib 実装 | コマンド  | 用途・引数                                       |
| ------------ | ------------- | --------- | ------------------------------------------------ |
| `0x840101d4` | `0x12ecb4`    | `0x20009` | open(mode) → handle、失敗時 null                 |
| `0x840101d8` | `0x12ecfc`    | `0x2000a` | close(handle)                                    |
| `0x840101dc` | `0x12ed2c`    | `0x2000b` | configure(handle, config)                        |
| `0x840101e0` | `0x12ed64`    | `0x2000c` | 再生開始(handle)                                 |
| `0x840101e4` | `0x12ed98`    | `0x2000d` | 録音開始(handle)                                 |
| `0x840101e8` | `0x12edcc`    | `0x2000e` | 停止要求(handle)                                 |
| `0x840101ec` | `0x12ee00`    | `0x2000f` | 停止要求と待機(handle)                           |
| `0x840101f0` | `0x12ee34`    | `0x20010` | seek(handle, position, flags)                    |
| `0x840101f4` | `0x12ee5c`    | `0x20011` | status(handle, out)                              |
| `0x840101f8` | `0x12ee94`    | `0x20012` | 再生バッファ補充(handle, index, length)          |
| `0x840101fc` | `0x12eee0`    | `0x20013` | 録音バッファ処理完了通知(handle, index, 第3引数) |

configure 以降は kernel の非ゼロを成功 `0`、ゼロを失敗 `-1` に変換する。
close はこの変換をせず、kernel の成功 `1` / 失敗 `0` を返す。
録音バッファ通知の第3引数は wrapper が渡すが、該当 kernel 分岐では参照していない。

SharpLib は `0xe6118` の thunk から kernel 公開入口 `0x600063c0` を呼ぶ。
system の `0x90a04` → `0x9006c` → `0x9be30` が音声コマンドのディスパッチ。
open の mode は再生 `0x10`、録音 `0x20` の2種類。
ハンドルは kernel 管理の `0x6c` バイトの状態領域を指す。アプリ側の free に渡さない。

## 設定構造体

kernel `0x9af64` が解釈する。ポインタは32ビット、整数は little endian。

| オフセット | 型      | 内容                                                           |
| ---------- | ------- | -------------------------------------------------------------- |
| `0x00`     | u32     | flags                                                          |
| `0x04`     | u32     | 全体のバイト数                                                 |
| `0x08`     | u32     | PCM サンプルレート                                             |
| `0x0c`     | u16     | PCM ビット数                                                   |
| `0x0e`     | u16     | PCM チャンネル数                                               |
| `0x10`     | pointer | バッファ0、またはファイル指定                                  |
| `0x14`     | pointer | バッファ1                                                      |
| `0x18`     | u32     | バッファ0の長さ                                                |
| `0x1c`     | u32     | バッファ1の長さ                                                |
| `0x20`     | pointer | flags `0x01000000` 時の追加フィールド。pvss はウィンドウを渡す |

**通常部分は32バイトだが、`0x01000000` 時は36バイト必要。**
ディスパッチのサイズ検査が32でも、実装は追加フィールドを読む。
kernel `0x2ccc8` はこのウィンドウを通知先として使用する。通知の詳細は後述。
flags はハンドル内の既存値に OR されるため、再設定で形式を安全に切り替えられるとは限らない。

確認した分岐は以下のとおり。

- `0x00000001`: ファイル指定。録音では拒否される。パスの文字コードなどは未確定。
- `0x00000200`: WAV 読み込み。`RIFF` / `WAVE` / `fmt ` / `data` と PCM format tag `1` を検査。
  `fmt ` の直後に `data` がある配置を要求し、任意の RIFF チャンクを走査する実装ではない。
- `0x00000400`: 圧縮音声のデコード。`TAG` の末尾タグ処理があり MP3 と推定するが、対応形式の全範囲は未確定。
- `0x00000100`: raw PCM。`0x9b520` で設定値を読み、`0x9c828` から PCM コピーへ進む。実機入力は未検証。

PCM 設定値の取り込みは `0x9b520`、形式検査は `0x9b544` 以降。
許可レートは 8000 / 11025 / 12000 / 16000 / 22050 / 24000 / 32000 / 44100 / 48000 Hz、
ビット数は8または16、チャンネル数は1または2。
8ビット PCM の符号、ステレオの並びなどの入力契約はまだ確認していない。

## 状態とシーク

status の出力は16バイト。kernel `0x9bd74` と `0x9bdf4` で以下を格納する。

| オフセット | 型  | 内容                                             |
| ---------- | --- | ------------------------------------------------ |
| `0x00`     | u32 | 動作状態（状態番号の意味は未確定）               |
| `0x04`     | u32 | 現在位置、ミリ秒                                 |
| `0x08`     | u32 | 全体の時間、ミリ秒。録音時の意味は未確定         |
| `0x0c`     | u32 | 内部バイト位置。WAV ヘッダー等を含む可能性がある |

seek (`0x9b950`) は flags の bit 0 でデータ開始位置基準、bit 1 で現在位置基準。
bit 0 が優先され、どちらもない指定は移動しない。
`0x100` があれば position はミリ秒、なければ秒として換算する。
pvss も `0x101` を指定して状態取得したミリ秒位置へ戻している。
圧縮音声ではバイト換算を経由しており、サンプル単位の正確なシークとは断定できない。

## 純正アプリの使用順序

pvss の `0x22795c` 以降で flags `0x01000400` とデータ、長さ、ウィンドウを設定し、
`0x227980` 以降で open(`0x10`) → configure → 再生開始を呼ぶ。
終了処理 `0x215064` 以降は停止待機 → close → 音声データ解放の順。
位置復元 `0x227484` 以降は status → 停止待機 → seek(`0x101`) → 再生開始。

メモリ指定ではアプリのポインタをハンドルに保持するため、音声データは非同期処理中も生存させる必要がある。
停止待機は内部状態を最大200回、待機関数への引数10で確認する実装で、無期限の完了保証ではない。
将来の安全なラッパーでは、停止 API の戻り値だけでバッファ解放可能と判断しないこと。

バッファ補充は `0x9c300`、録音側の通知は `0x9c360`。
状態領域には2本のバッファがあり、index に応じて12バイト刻みで更新する。
この分岐に index の上限検査は見当たらないため、ラッパーでは `0` / `1` に制限する必要がある。
消費通知に合わせて補充する。空バッファ時の復旧と実機の処理時間には追加確認が必要。

## Doom の連続 PCM 出力

純正アプリとの比較と、バッファ枯渇時の追加解析は
[長い音声のバッファリング](#長い音声のバッファリング追加解析)を参照。

`0x9cbe0` は消費済みバッファの index を kernel イベント7に格納し、`0x9af14` で送信する。
`0x2cc84` からの変換で PEG の kind `0x107`、param `5`、
`ext_params[0]` が index、`ext_params[1]` が内部バイト位置になる。
`0x9c300` の補充 API は length を設定して読み取り位置をゼロに戻す。

Doom は PureDOOM の `doom_get_sound_buffer()` から512フレーム分（ステレオ1024サンプル）を取り出す。
配列の確保サイズは2048サンプルだが、`I_UpdateSound()` が生成する範囲は1024サンプル。
消費通知ごとに512フレームのミックスを2回実行し、2本の4096バイトバッファを交互に補充する。
ゲーム描画の35Hzとは別に、音声消費に合わせて進める。BGMはRustのMUSシーケンサーとOPL音源で同じPCMへ混合する（[詳細](../crates/brain-doom/README.md#bgm)）。

標準の内部 PCM バッファは `0x9bf64` 以降で2本とも32768バイトに設定され、
11025Hz・ステレオ16bitでは1本だけで約743msになる。
DoomはOPL音源の軽量化と同時に、内部・外部とも4096バイトへ短縮して描画待ち時間を減らす。
4096バイトなら1本約93msだが、DoomのBGM合成では補充が間に合わない可能性がある。内部バッファと入力バッファによる発音遅延は残る。
Inspectorは比較用に2048〜32768バイトを選択でき、短い設定だけ内部長を変更する。

初回 start は両バッファを同期的に先読みするが消費通知を送らないため、戻った直後に両方を補充する。
終了時は停止待機と status の state `0` を確認してから close し、最後にアプリを終了する。
停止を確認できなければエラー画面に残して、PCM バッファを含むアプリイメージの解放を防ぐ。
ゲーム側の混合や音声 API に失敗した場合も `DOOM ERROR  Q EXIT` に移る。
長時間の再生は約13.5時間分の total_bytes に制限しており、無期限ストリームではない。

## ホスト音量

実機報告では音量は **0〜9**、純正アプリで変更して終了するとホストにも反映される。
共通設定 API と再生セッション用 API は別系統。解析結果は下記参照。
Doom は起動・終了時にはホスト音量を書き換えず、PageUp/PageDownの押下時にReflexの保存用音量APIを呼ぶ。
Shift併用でも同じ音量操作になる。Inspectorで確認済みのAPIだが、Doom内での操作は実機確認待ち。
Doom メニューの SFX Volume はエンジン内の混合音量であり、ホストの0〜9とは別の値。

## 残る調査

音量・ミュート・スピーカー／ヘッドホン切替、通知イベント、録音の実例、競合時の所有権を確認する。
VoiceRec には `.WAV` と `WAVE` の文字列があるが、上記 SharpLib 入口のリテラルは見つからず、
同じ公開 API を使うとはまだ言えない。
kernel には `audio_codec_init_common()`、`AUDIO:WR`、`AUDIO:RD` などのログがあるが、
これだけではコーデック型番や直接アクセス用の ABI は確定しない。

## ホスト音量と Inspector の標準 Stream

V690_H1 には保存用音量と再生セッション用音量の2系統がある。
以前は `0x10015` で再生用 `0x2000601c` だけを書き換えており、
実機ではアプリ終了後に音量が元に戻った。保存されるという以前の説明は誤り。

Reflex の `volume` / `set_volume` は純正 pvss と同じ SharpLib API を使う。

- 取得 `0x84010054` → file `0xf7d64` → syscall `0x3000d`
- 設定 `0x840100bc` → file `0xf7d28` → syscall `0x3000e`
- 設定関数の返り値は変更前の音量。成功フラグではないため、設定後の読み戻しで確認する。

kernel の `0x905a0`〜`0x905e0` が設定ID6を処理し、
`0x945d0`〜`0x94604` は0〜9を検証して `0x6000201c` に保存、
`0x95fc8(1, 1, 0x4000)` でシステムに設定変更を通知する。
pvss の `0x21326c` / `0x2132f0` も増減後に `0x212128` のthunkからこの公開APIを呼ぶ。
再生用RAMへの直接書き込みと音声ドライバーへの直接通知は廃止した。
Inspectorでは修正版の再生中の反映と終了後の保持を実機確認済み。電源断をまたぐ保持は未検証。

下位PCM転送 `0x17ef9c` は4096バイトの出力先を満たす処理で、
`0x17f01a`〜`0x17f030` では内部バッファの残り長にコピーを制限する。
Inspector の W は2048バイトへの短縮をやめ、標準32768バイトで補充を検証する。
これで通知間隔にも余裕ができるが、無音の原因が短縮だけだったとはまだ断定できない。
Inspector の標準32768バイトでWの連続再生が鳴ることは実機報告済み。さらに4096バイトで安定再生が報告された。ただしDoomではBGM合成追加後に音声が停止する報告があり、32768バイトへ戻した。実機の補充時間は最大689msで、音声再生中1〜2 FPS、音声停止後20 FPSと報告された。このためOpalへの変更と4096バイトへの短縮を行い、実機で再計測する。

## ストリームの自動復旧

Reflexの `audio::cursors` はInspectorが参照していたV690_H1の入力カーソル
（ハンドル+0x4c/+0x58）を読み出す。`StreamWatchdog` は
`[0, buffer_bytes]` または逆順が続き、再生バイト位置も進まない状態を検知する。
正常なバッファ境界通過や、同じカーソルでも再生位置が進む状態では再起動しない。

Doomは250ms間隔で監視し、1秒間の停止で既存の音声リセットを実行する。
Inspectorはタイマーで監視し、連続再生（W）だけを対象とする。
待機時間は1秒と4バッファ分の再生時間の長い方で、32768バイト時は約3秒。
単発再生（Q）、手動停止（P）、API失敗後は自動再起動しない。
再起動の試行回数を `RESTART` に表示する。再初期化失敗時は再試行を続けず、
既存のAPI結果表示に失敗を残す。停止確認に失敗したハンドルは解放しない。

カーソルの単発観測だけでは停止とは断定できないため、進行停止を併せて確認する。
この復旧処理で実機の無音が回復するかは未確認。

## 長い音声のバッファリング（追加解析）

以下は V690_H1 の静的解析。アドレスは各バイナリのファイルオフセット。
「実装が存在すること」と「実機でその経路が選ばれること」は区別する。

### pvss：音声全体をメモリに用意する

`App/pvss/AppMain.bin` の `0x2278d0`〜`0x227934` は音声の長さ分の領域を
確保し、コピーしたデータ全体に XOR 処理を行う。
`0x22795c`〜`0x22797c` では flags `0x01000400`、全体長と同じバッファ0長、
そのデータポインタを設定する。補充 API `0x840101f8` のリテラルもない。
この経路は圧縮データ全体を渡してホストに順次デコードさせる方式であり、
アプリが小さい PCM バッファを継続生成する Doom とは異なる。

### ATR CALL 5000：全体指定と二重バッファの両方を実装

`App/ATR_UG/AppMain.bin` には PCM の二重バッファ補充処理がある。

| 処理           | オフセット           | 内容                                                                                                |
| -------------- | -------------------- | --------------------------------------------------------------------------------------------------- |
| 容量設定・確保 | `0x3eac8`〜`0x3eb38` | 引数 `n` に対し1本 `44100 * n` バイト、2本確保。`n == 0` は1024バイト、`n == -1` は二重バッファ無効 |
| 初期化         | `0x3ed30`〜`0x3ed84` | 元データ・全体長・送信位置を保存。PCM、22050Hz、16bit、mono                                         |
| 初回データ準備 | `0x3ed88`〜`0x3eed0` | 各バッファに `min(容量, 残量)` をコピーし、送信位置を進める                                         |
| 全体指定の分岐 | `0x3eed8`〜`0x3ef2c` | 二重バッファ無効なら、元データ全体をバッファ0に指定しバッファ1を空にする                            |
| 再生           | `0x3ef4c`〜`0x3ef78` | open → configure → start。直後の再補充はない                                                        |
| 消費通知処理   | `0x2eb48`〜`0x2eb98` | param `5` の通知から index と位置を取り出し補充処理へ渡す                                           |
| 補充           | `0x3ef88`〜`0x3f16c` | 通知された側に次のデータをコピーし `submit(handle, index, length)`。残量0なら submit しない         |

コピー先は固定の2本、コピー元は保存済みのメモリポインタ＋送信位置。
`0x73a10` はメモリコピー実装であり、この補充処理自体がファイルを読むわけではない。
22050Hz・16bit・mono は毎秒44100バイトなので、通常引数は秒単位の容量と解釈できる。
ただし確認した初期化呼び出し `0x3de64` は `n = -1`。
**二重バッファ実装の存在は確認できたが、通常操作での有効化や実際の容量は未確定。**
「純正は必ず大容量二重バッファを使う」とはまだ言えない。

### ホスト内部：入力と PCM 転送用バッファは別

入力2本のほかに、ホストが標準32768バイト×2の PCM バッファを持つ。
開始時 `system.bin:0x9b88c`〜`0x9b91c` はこの2本を同期的に埋める。
この先読みでは消費フラグの返り値を通知に変換しない。
通常再生中の `0x9cc24`〜`0x9ccf8` は空いた内部バッファを埋め終わってから、
その処理で消費した入力バッファの通知をまとめて送る。
したがって、入力の消費通知はスピーカーがその入力を再生し終えた通知ではない。

ファイル指定の場合は `0x9cbe4`〜`0x9cc10` が別経路に入り、
アプリへ消費通知を送る代わりに `0xa0724` を呼び、その戻り値を入力長へ格納する。
メモリ指定は `0x9cc14`〜`0x9cc20` でイベント7を送る。
ファイル経路の読み込みAPIの詳細と純正アプリの呼び出し例は未確定。

### 枯渇時：単純な「補充すれば再開」にはなっていない

PCM コピー `0x9c830`〜`0x9c8bc` は選択中の入力からコピーし、
正のバイト数をコピーしてその入力を使い切ったときに、次の入力へ切り替える。
最初から残量0なら `0x9c84c` で後処理へ飛び、ここでは入力を切り替えない。

両方の入力が空になった場合、通常の非ループ再生では内部バッファの残りを
ゼロで埋め、返り値に bit 2 (`4`) を立てる (`0x9cba8`〜`0x9cbcc`)。
呼び出し側の `0x9cca4`〜`0x9cccc` はこのビットを見ると、
**蓄積した消費通知フラグをゼロにして**、全体の終端前ならイベント9を送る。
その回の通常のバッファ消費通知は送られなくなる。
イベント9の最終的なUI通知との対応は未調査。

さらに、以下の状態では静的な制御フロー上、補充ループが進まない。

1. 選択中の入力は使い切っている。
2. もう片方にはデータがある（遅れて submit された場合など）。
3. 内部バッファにはまだ埋める領域がある。

このときコピー量0で後処理へ飛ぶが、「両方空」でもないためゼロ埋めも行わない。
`0x9c7dc` が残り要求量を減らさず返り、`0x9cc94`〜`0x9cc9c` が再び呼ぶ。
submit (`0x9c340`〜`0x9c358`) は長さとカーソルだけを更新し、
選択中の入力 index は変更しない。
この経路は報告された `cursor = [0, bufSize]` または逆順での停止と整合するが、
実機の停止時に選択 index (`handle + 0x5c`) を観測していないため、原因確定ではない。

### 現在の Reflex / Doom との差と次の検証

Doom は入力・内部とも4096バイトにし、開始時に入力2本を使い切ってから
`fill → submit` を2回行う。再生中も通知を受けてから音源合成を行う。
純正で確認した全体データ指定よりも枯渇しやすく、合成が遅れれば上の経路へ入り得る。
再起動監視だけでは、この補充遅延の原因は解消しない。

次は Inspector で内部長と入力長を別々に扱い、開始時の先読み後にも入力が残る構成を
比較するのが妥当。合わせて選択 index、両カーソル、再生位置、通知の param を記録する。
入力を大きくすると通知後の一括合成も重くなるため、Doom では事前に小分けで合成し、
補充通知への応答はコピー主体にする方式を検討する必要がある。
今回は解析記録のみを更新し、再生コードやバイナリは変更していない。
