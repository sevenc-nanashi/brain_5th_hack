# V690_H1 PCConnect・USB通信の解析

`PCConnect/AppMain.bin` と `system.bin` の静的解析結果。
以下のAPI名は解析用の仮称。実機での呼び出し・PCとの転送は未検証。
アドレスはこの更新パッケージ限定で、別機種・別バージョンへそのまま適用しない。

## 結論

アプリから使える送受信入口がある。PCConnectは共通API `0x600063c0` を介して
kernelの通信バッファを読み書きしている。
その先にはUSB Mass Storageの特定セクターを独自パケットとして扱う経路がある。
アプリで読み出せるメモリをこの経路に流し、PCで保存するダンパーは実装候補になる。
ただし、APIの送信成功はkernelバッファへの格納を意味し、PCでの受信完了ではない。

## 対象とアドレス

- PCConnect: `packages/001/ROM/ToolsApp/PCConnect/AppMain.bin`、154134 bytes。
  SHA-256: `277356bb5b00fcaad74ccfcd1a047e11121bf9c0c5c0d76c8c2774f3f8f7e609`
- system: `system.bin`、1694720 bytes。
  SHA-256: `315a695c25669c00b46fbcee6c17e13f6959a879e895844d93fb652f1b00f21d`

公開入口だけ実行時アドレス。それ以外の位置は各ファイルのオフセット。
systemの実行時アドレスはファイル位置に `0x60002400` を加える。
PCConnectの推定ロード先は `0x90000000`。

呼び出し経路:

```text
PCConnect 0x156c4: LDR pc → 0x600063c0
system 0x3fc0 → 0x90a04 → 0x9006c → 0x9e4a0
```

`0x90a04` はコマンド上位16 bitで振り分け、`0x20000` 系を `0x9006c` に渡す。
USB関連はさらに `0x9e4a0` に渡る。SharpLibのラッパーを経由する必要はない。

## 共通APIとコマンド

命令列から復元した引数配置:

```c
// 0x600063c0、ARM状態。型名・関数名は仮称。
u32 control(u32 command, const void *input, u32 input_size,
            void *output, u32 output_size, u32 *transferred);
```

最初の4引数は `r0..r3`、最後の2引数は呼び出し時のスタック。
送信でもデータを第4引数へ渡す点に注意。

| command | system分岐 | 復元した動作・条件 |
| --- | --- | --- |
| `0x2002b` | `0x9e550` | USBタスクへ接続開始要求を送る。非同期 |
| `0x2002c` | `0x9e564` | USBタスクへ切断要求を送る。非同期 |
| `0x2002d` | `0x9e578` | 公開するドライブ／モードの選択。`VRM:` と4-byte出力を渡す場合だけ選択状態の照会になる |
| `0x20034` | `0x9e828` | 受信バッファから `output` へ最大 `output_size` bytesコピー。実際の長さを `transferred` に格納 |
| `0x20035` | `0x9e884` | `output` の `output_size` bytesを送信バッファへコピー。格納した長さを `transferred` に格納 |
| `0x20036` | `0x9e8e0` | 送信バッファ消去。非nullのinputと `input_size == 4` が必要 |
| `0x20037` | `0x9e91c` | 受信バッファ・組み立て中パケットを消去。同じくinputの4 bytes検査がある |
| `0x20038` | `0x9e990` | 通信状態を4 bytesで取得。通信有効時のみ成功 |
| `0x20039` | `0x9eb5c` | 接続状態の内部値を1 byteで取得。出力しても戻り値は0のまま |
| `0x2003a` | `0x9e9ec` | 通信有効化。非nullのinputと `input_size == 4` が必要。受信バッファも消去 |
| `0x2003b` | `0x9eb24` | 通信無効化。同じくinputの4 bytes検査がある |
| `0x2003d` | `0x9ebb8` | 条件付きモード切り替え要求。引数不要だが、単純なopenとは断定しない |

`0x20034/35` は有効フラグが立っていなければ転送せず、処理後の戻り値だけでは
実際の転送量が分からない。`transferred` を0で初期化し、長さを別途確認する必要がある。
送信バッファは `0xafc6c` で必要に応じて拡張されるため、PCが読まないまま大量に送信しない。

PCConnectの具体例:

- `0x1f4bc..0x1f4f4`: `control(0x20034, 0, 0, buffer, 0x602, &received)`。
- `0x1f570..0x1f5ac`: `control(0x20035, 0, 0, data, length, &written)`。
  要求長とwrittenを比較している。
- `0x1f5c8`: `0x20038` の状態bit `0x20` を調べる。
  system `0x9f758..0x9f77c` では受信バッファにデータがあるとbitを立てる。
- `0x16b90..0x16bd8`: `0x2003a/3b` で通信を有効／無効化する。
- `0x15a08`: `VRM:` を `0x2002d` に渡し、4-byteの出力を返す。
  この呼び出しだけで常にDRMモードになるとは言えない。

**純正アプリの呼び出しをそのままコピーできない箇所もある。**
PCConnect `0x1f858` は `0x20037` を `input=null, input_size=0` で呼んでいるが、
このsystemでは入力検査で戻る。`0x1f61c` にも同形式の呼び出しがある。
また `0x20039` は一般的な「戻り値非ゼロなら成功」という扱いにできない。

## PC側はUSB Mass Storage

systemのUSB設定記述子は `0xf29d4` と `0xf29f4`。
interfaceのclass/subclass/protocolは `08/06/50`、endpointはOUT `0x01` とIN `0x82`。
最大パケットサイズはそれぞれの記述子で64 / 512 bytes。
`08/06/50` はMass Storage・SCSI・Bulk-Only Transportの組み合わせである。
参照: [Microchip AN1142](https://ww1.microchip.com/downloads/en/DeviceDoc/01142A.pdf)、
[USB-IF Bulk-Only Transport](https://www.usb.org/document-library/mass-storage-bulk-only-10)。

したがって、この経路でPCから単にbulk endpointを読むだけでは足りない。
ストレージの読み書きと独自パケット形式を扱う必要がある。

system `0xd7fac` の52-byte単位のテーブルには次のモードがある。

| 入力名 | 内部mode |
| --- | --- |
| `SD0:` | 6 |
| `ROM:` | 5 |
| `SYS:` | 2 |
| `USR:` | 4 |
| `AKM:` | 3 |
| `LOG:` | 1 |
| `DRM:` | 7 |
| `VRM:` | 8 |

`0x2002d` の照会分岐は入力先頭4 bytesが `VRM:` かつ出力先が非null・4 bytesのときだけ。
戻り値は照会処理の成否、出力は現在選択中の名前が `VRM:` なら1、それ以外なら0。
`DRM:` と出力先を渡してもDRM選択状態の照会にはならない。
モード設定は内部の接続開始済みフラグ（状態領域 `+0x10c`）が0のときだけ実行する。
ROMなどをストレージとして公開する別案も考えられるが、公開範囲や書き込み可否、
動作中のファイルシステムとの排他は未確認。RAMダンプとは別の経路になる。

## DRMモードの通信セクター

system `0x9ee60` が読み出し、`0x9f0f4` が書き込みの処理。
内部modeが7で通信有効のとき、次の1セクターアクセスを特別扱いする。

| LBA | 動作 |
| --- | --- |
| `0xFFD` | データパケットの読み書き。読み出しが辞書→PC、書き込みがPC→辞書 |
| `0xFEC` | 制御・状態パケットの読み書き。状態読み出しにも事前の条件がある |

送信経路は `0x9e884` → kernelバッファ → `0x9ef38` → `0xafe04` →
512-byteのセクターへコピー。受信は `0x9f154` → パケット検証・組み立て →
`0x9f248` → `0xafd4c` → kernelバッファ → `0x9e828`。
これらは通常のファイルへの書き込みではない。

データパケットについて復元できた部分（セクター内オフセット）:

| offset | 内容 |
| --- | --- |
| `0x00` | 16-byteの識別子 `SHDIC COMM KEYWD`（NULを含めない） |
| `0x10` | ヘッダー長。送信データパケットでは `0x2c` |
| `0x14` | 純正生成値は `0x210 \| (device_version << 16)` |
| `0x18` | データパケットの生成値は1、制御パケットは0 |
| `0x1c` | このパケットに含まれるペイロード長 |
| `0x20` | チェックサム。計算時は `0xffff0000` を置く |
| `0x24` | 組み立て対象の合計データ長。辞書からの送信では単体の長さと同じ |
| `0x28` | 連番 |
| `0x2c` | ペイロード開始。最大468 bytes |

根拠は `0xaf904`、`0xaf960`、`0xafe04`、`0xaf750`。
内部C++オブジェクトの先頭4 bytesはvtableで、セクターには含まれない。
チェックサムは512 bytesのバイト和を16 bitへ切り詰め、
下位16 bitに和、上位16 bitに `0xffff - 和` を格納する。
検証側 `0xaf834` はチェックサム欄を含む512 bytesをそのまま加算する。
上下16 bitが互いの補数なので、チェックサム4 bytesの和は常に510で、
生成時の仮値 `0xffff0000` と一致する。チェックサム欄をゼロにして計算してはいけない。

`0xaf898` は識別子、長さ、仮想関数、チェックサムを検査する。
このデータ／制御クラスの仮想関数は `0x10edf8` の固定値1であり、
`0x14/0x18` の一致をこの経路では検査していない。
ただし、PC側の受信器は既知のヘッダー長と単体長を自分でも検査する。

## 状態照会・再送・ACK

制御パケットは512 bytes、ヘッダー長 `0x34`、単体ペイロード長4。
`0x34` にlittle-endian u32の制御値を置いてLBA `0xFEC` へ1セクター書く。
実装は `0x9f2d8..0x9f3b4`。認識する制御値は2と3だけ。

| 制御値 | 動作 |
| --- | --- |
| 2 | 再送要求フラグ `0x08000000` を立てる。次の `0xFFD` 読み出しは現在保持しているパケットを再取得する |
| 3 | 状態応答待ちフラグ `0x2` を立てる。次の `0xFEC` 読み出しで状態を返す |

状態応答も制御パケットで、`0x34` から4 bytesが状態値。
読み出し時に `0x2` を落としてから応答を組み立てるため、状態を再度読むには
制御値3を書き直す必要がある。失敗したデータ書き込みでも状態応答待ちになる場合がある。

| 状態bit | 復元した意味 |
| --- | --- |
| `0x1` | アプリ側通信有効 |
| `0x10` | 未送信データ、または送信リストの次要素がある。現在保持中の最終パケットだけでは立たない |
| `0x20` | アプリがまだ読んでいない受信データがある |
| `0x100` | 直前のパケット書き込み処理で成功側に進んだ |
| `0x200` | 直前のパケット書き込み処理でエラー側に進んだ |
| `0x08000000` | 次のデータ読み出しで現在パケットを再送する |

`0x100/0x200` は次の書き込み処理で消す（`0x9f174`、`0x9f2f8`）。
上位側のエラー値はORで蓄積される箇所があるため、全ビットを「直前の結果」とは扱わない。
不明な識別子のパケットは通常の仮想ディスク書き込みへ進む場合もあり、
SCSI書き込み成功だけで通信パケットの受理を判断できない。

辞書→PCの通常読み出しは `0x9ef10..0x9ef78`。
再送要求がなければ現在パケットから次へ進み、必要なら送信バッファから新しいパケットを作る。
再送要求があれば現在パケットを進めず、その読み出しで要求フラグを落とす。
**この経路に独立した成功ACKコマンドは見つからず、次の通常読み出しが前進操作になる。**
読み出したパケットを検証・保存する前に次を読むと、再送で戻せる位置も進んでしまう。

PC→辞書は `0x9f194..0x9f274` で組み立てる。
同じ連番を組み立て中のリストへ再送すると、その要素を置き換える（`0xafb14`）。
単体長の合計が合計データ長以上になった時点で受信バッファへ移してリストを破棄する。
**完了済み転送の連番を記憶して重複排除する処理は、この経路にはない。**
タイムアウト後の無条件再送でアプリへ重複配信される可能性があり、
ダンプ要求のIDと応答の位置は上位プロトコルでも管理する必要がある。

### 状態照会パケットのオフライン例

versionを `0x0103` と仮定した制御値3の先頭64 bytes。残り448 bytesは0。
機器から採取したパケットではなく、復元した構造から生成した例。

```text
53 48 44 49 43 20 43 4f 4d 4d 20 4b 45 59 57 44
34 00 00 00 10 02 03 01 00 00 00 00 04 00 00 00
aa 06 55 f9 00 00 00 00 00 00 00 00 00 00 00 00
00 00 00 00 03 00 00 00 00 00 00 00 00 00 00 00
```

512 bytesのSHA-256は `95b9cf45a41ee233a47fc6cb333a724acfe6d6b90c4eaaf5a98fbe6bf8c3793e`。
制御値2ならoffset `0x34` は2、チェックサムは `0xf95606a9`。

kernelの命令を実行した検証や、実機が受理することの確認ではない。

## 通信開始順序の候補

静的解析から組んだ実機検証用の順序であり、成功実績のある手順ではない。

1. 接続前に `control(0x2002d, "DRM:", 4, NULL, 0, NULL)` でモードを選択する。
   `VRM:` の照会とは区別する。すでに接続開始済みなら設定は失敗する。
2. `control(0x2002b, NULL, 0, NULL, 0, NULL)` で接続開始を要求する。
   戻り値1はイベントの要求であり、列挙完了ではない。
3. 接続状態を確認し、`control(0x2003a, &dummy, 4, NULL, 0, NULL)` で通信を有効化する。
   dummyは0で初期化する。kernelはこの入力値を読まない。
4. アプリが小さな既知データを `0x20035` で格納し、PC側で制御値3→状態読み出し→
   `0x10` の確認→データ読み出しを行う。単体長・チェックサム・内容を照合する。
5. 破損時は次を読む前に制御値2を書き、同じ連番を再取得できるか確認する。
6. 終了時は `0x2003b` で無効化して `0x2002c` で切断を要求する。
   切断完了と通常モードへの復帰は別途確認する。

順序の根拠はUSBタスク `0x9df84` と接続処理 `0x9e030`。
DRM接続開始の `0x9e158..0x9e190` は通信状態を0へ戻すため、
**通信有効化を接続開始より前に済ませても維持されない。**
`0x20039` の接続状態は初期値0の1-byte変数で受け、出力値を確認する。
列挙・アプリ通知との正確なタイミングは実機で確かめる必要がある。

PCConnect自身にも別の上位同期処理があり、`0x1f890` 以降に
`PC end SYNC(Quit)`、PC送信コマンド1/3/5/7/9、辞書送信2/4/6/8の文字列がある。
独自ダンパーでこの上位プロトコルまで再現する必要があるかは、実機で切り分ける。

## ダンプ実装に向けた次の確認

1. 実機のUSB記述子と、純正PCConnectの接続・終了時の通信を採取する。
2. DRMモード選択、有効化、切断時の復旧を小さなアプリで確認する。
3. 固定文字列を1パケット送り、PC側で状態照会・LBA `0xFFD` の読み出し・検証・再送を確認する。
4. 成立した経路に、アプリで読めるメモリの範囲指定、分割転送、長さとハッシュの照合を追加する。

PC側のセクターI/Oは対象デバイスを確実に識別し、OSのキャッシュや自動マウントとの競合を避ける必要がある。
特定LBAへの書き込みはDRMモードでのみ通信として解釈されるため、通常のSDカードや
別モードのドライブへ同じ書き込みを試してはいけない。
固定文字列を使う実験アプリ [brain-usb-probe](../crates/brain-usb-probe/README.md) と、
Linux SG_IOで状態照会・受信・再送確認を行う `scripts/usb-probe.rb` を追加した。
固定文字列の受信と再送一致は実機で確認済み（末尾参照）。
共通のUSB APIラッパーやメモリダンパーへの組み込みはまだ行っていない。

## 実機の接続確認（2026-10-30）

WSLのUSB接続で `04dd:92e1` を確認した。以下は静的解析ではなく実機の観測値。

- 製品名: `SHARP Mass Dictionary`、`bcdDevice=1.01`。
- interface: `08/06/50`。bulk OUT `0x01`、bulk IN `0x82`、最大パケットサイズ512 bytes。
- Linuxドライバー: `usb-storage`。確認時のblock deviceは `/dev/sde`、SCSI genericは `/dev/sg4`。
  デバイス名は再接続で変わるため固定しない。
- 容量: 411648セクター × 512 bytes = 201 MiB。
- 先頭512 bytesはFAT16のブートセクター。OEMは `GR-FILE `、末尾は `55 aa`。
  予約領域6セクター、FATは2面・各201セクター、ルートディレクトリ512エントリー、
  1クラスタ8セクター。データ領域の開始LBAは440。

USB記述子と先頭セクターだけを読み取り、書き込み・マウント・モード変更は行っていない。
通常のFAT16ディスクが公開されており、解析したDRMの仮想ディスクとは容量・versionが異なる。
現在どの内部ドライブが選択されているかは、この情報だけでは断定できない。
**VID/PIDだけではDRMモードを判別できない。** このディスクでは `0xFEC/0xFFD` は
FAT16のデータ領域に入るため、通信要求の書き込みを試す段階ではない。
次は本体側アプリでDRMモードへ移行し、再列挙後にモードと記述子を確認する必要がある。

### UsbProbeでのDRM接続・転送結果

上記の通常モード確認に続いてUsbProbeを配置し、本体でEnterを押した後に
`Hello queued. Read on PC.` が表示された。Windowsでは2 MiBのディスクとして再列挙された。
通常のWSLアタッチはWindows側の使用中エラーになり、管理者権限による
`usbipd bind --force --busid 5-1` と再アタッチの後で通信できた。

- Linuxからの照会: `04dd:92e1`、revision `0103`、4096 × 512 bytes。
- 制御値3の状態照会応答: `0x101`。通信有効だが未送信bit `0x10` は0。
- 制御値2で保持済みパケットを取得: データ長40、連番0。
- 内容: `REFLEX USB PROBE v1\n` が2件連結されていた。
- チェックサム検証に成功。再度制御値2を書いた後の512 bytesは完全一致。

これによりアプリ→kernel→USB→PCの転送、PCからの制御要求、状態応答、
保持済みパケットの再送を実機で確認した。
当初の受信器は未送信bitだけを待ってタイムアウトしたため、bitが0なら
保持済みパケットを再送要求で取得するよう修正した。

固定文字列が2件になった理由は未解明。kernelの送信バッファ残存やアプリ側の
実行回数などを切り分ける必要があり、単発送信・重複なしの保証はまだできない。
最初のパケットを読み出した主体も未特定で、WindowsやLinuxの自動走査とは断定しない。
Escで本体アプリが終了したとの報告後、Linuxで `USB disconnect, device number 4` を確認し、
Windowsのusbipd一覧とLinuxのlsusb一覧からBrainが消えたことも確認した。
大容量ダンプ、通常のPCConnectへの復帰、重複なしの単発送信は未確認。

## Explorerのファイル送信

`brain-explorer` のSend to PCと `scripts/usb-receive.rb` は上記DRM通信の上に
要求・応答プロトコル `BRNFILE3` を載せる。PCが指定するのは読み出し位置のみで、
送信対象はBrainの画面で選んだファイルまたはフォルダーに固定する。

整数はlittle-endian。PCからの要求は28 bytes。

| offset | 内容 |
| --- | --- |
| 0 | `BRNFILE3`（8 bytes） |
| 8 | PCで生成したランダムなセッションID（8 bytes） |
| 16 | 圧縮前ストリーム内の位置（u64） |
| 24 | コマンド（u32、1=読み出し、2=受信完了） |

Brainからの応答は44-byteヘッダーとzlib形式の圧縮データ。元データは最大65536 bytes、
圧縮データは最大66560 bytesに制限する。DEFLATE level 1で各ブロックを独立して圧縮する。

| offset | 内容 |
| --- | --- |
| 0 | `BRNFILE3`（8 bytes） |
| 8 | 要求と同じセッションID |
| 16 | 要求と同じ位置（u64） |
| 24 | 圧縮前の合計サイズ（u64） |
| 32 | 続く圧縮データの長さ（u32） |
| 36 | 要求と同じコマンド（u32） |
| 40 | 圧縮前のデータ長（u32） |
| 44 | zlib形式のデータ（コマンド2では空、両方の長さも0） |

一度に未完了の要求は1件。読み出し位置は0から順番で、完了要求はファイル末尾のみ。
空ファイルも位置0の読み出しと完了要求を行う。同じ要求の連続受信は応答を再格納せず
無視する。PCは制御値2でkernelに保持された応答を再読出しできる。
PCは前の位置の応答や別セッションの残存応答を保存せず、分割された応答を組み立てる。
送信開始時は通信有効化後に `0x20036`（非nullの4-byte入力）で送信バッファを消去する。

元ファイルは転送中開いたまま保持し、長さの変化・読み出し失敗はエラーにする。
64-KiB単位で読み出すため、ファイルサイズに比例したメモリー確保はしない。
入出力バッファはヒープ上に確保する。圧縮処理はDoomと同じスタック切り替え方式で、
専用の128-KiBスタック上で動かす（初期化で約64 KiBを使用）。
PC側は展開出力をブロックの元サイズまでに制限し、チェックサム・終端・余分な入力を検査する。
タイムアウト時の自動再要求や再開は行わず、Escで切断して新しいセッションを開始する。
完了応答後もユーザーがEscを押すまで接続を維持し、PCが応答を読めるようにする。

ホスト上では実装したRustの要求処理とRubyの受信器を接続した一時的な自己チェックで、
空ファイル・1/65535/65536/65537/131073 bytesのランダムデータ、重複要求・応答、分割応答、保持パケットの再読出し、
チェックサム破損・不正要求・上書きの拒否と失敗時の一時ファイル削除を確認した。
これは実機USBやファイルシステムの動作確認ではなく、Explorerの実機転送は未確認。

旧BRNFILE1/BRNFILE2とは非互換なので本体・受信器を同時に更新する。
PCは受信成功後の固定50 ms待機を廃止し、未着時のみ5 ms待機する。
本体のポーリングタイマーは10 ticksから1 tickへ短縮した。
PCのRaw表示は展開して保存したバイト数、USB表示は成功したDRMセクターI/O回数×512 bytes。
制御・再送をUSB転送量に含めるが、SCSIヘッダーやUSB物理層の転送量は測っていない。
速度は最初の要求からの単調増加時計による経過時間で割った平均値（KiB/s）。

### フォルダーのストリーム（BRNTREE1）

フォルダーはBRNFILE3の圧縮前データとして、次のストリームを流す。
外側の位置・総量・Raw速度はメタデータ込みのストリーム長を表す。
最初に `BRNTREE1`（8 bytes）とレコード数（little-endian u32）、
続いて各レコードを親フォルダーが先に現れる順番で並べる。

| レコード内offset | 内容 |
| --- | --- |
| 0 | 種別（u8、1=フォルダー、2=ファイル） |
| 1 | 相対パスのバイト長（u32） |
| 5 | ファイルサイズ（u32、フォルダーは0） |
| 9 | 相対パスの生バイト列（区切りは `/`） |
| 9+パス長 | ファイル内容（フォルダーでは空） |

最初のレコードは空のパスのルートフォルダー。その後のパスは空であってはならない。
4096件制限は撤廃した。レコード数は形式上u32、元パスは259 bytesまで。
合計と位置はu64で、2 GiB制限はない。
各ファイルのサイズはOS APIと同じu32のため4 GiB未満。
本体は深さ優先で事前走査して件数と総量だけを数え、再走査しながら送信する。
祖先のディレクトリーハンドル・パスだけを保持し、内容は1ファイルずつ開いて読み、
サイズを検査して閉じる。2回の列挙で件数が変わった場合はエラーにする。
PCも全パスの一覧をメモリーに保持せず、一時フォルダー内の親と排他的作成で検査する。
PC側は `--directory` で展開し、絶対パス・空要素・`.`・`..`・NUL・バックスラッシュ、
重複パスや親が先にないレコードを拒否する。シンボリックリンクのレコードは扱わない。
プライベートな一時フォルダー内に作成し、全件確認後にLinuxの
`renameat2(RENAME_NOREPLACE)` で保存先へ公開する。失敗時は一時フォルダーを削除する。
名前の文字コード変換、時刻や元パーミッションの復元はしない。
単一ファイルもBRNFILE3を使い、旧受信器とは非互換。

ホスト上で本体のSource・圧縮・要求処理とPC受信器を接続し、サブフォルダー、空のルート、
空フォルダー、空ファイル、非UTF-8名、チャンク境界を超える内容を確認した。
パストラバーサルの拒否、破損時の一時フォルダー削除、受信中に作られた保存先への
上書き拒否も確認した。実機での再帰転送は未確認。

64ビット化後、ホスト上の一時的な自己チェックで2 GiB・4 GiBをまたぐ位置の
要求・応答・完了確認を検証した。3 GiBの疎ファイル2個から計6 GiB超の一覧を作り、
合計値と先頭ブロック、PC側の3 GiBファイルレコード受理も確認した。
これは数GiB全体の実機転送を検証したものではない。

4096件制限の撤廃後、ホスト上で単一フォルダー内の5000ファイルとネストした空フォルダーを
含む計5004レコードを、実装した列挙・圧縮・転送・展開処理で往復し、全ファイルの内容を
確認した。実機での多数エントリー送信と、多数の祖先ディレクトリーハンドルは未確認。
